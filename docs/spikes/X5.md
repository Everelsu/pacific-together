# Spike X5: tunnel UE packets through a sendto/recvfrom hook

Question: can the C++ layer move the game's own UE network traffic (the listen server's `IpNetDriver` UDP socket) onto a
link of our choice, so that the M6 Steam transport only has to swap the link? First link: loopback UDP.

Code: `native/PacificTogetherNative/transport.cpp` / `transport.hpp` (native layer 0.0.3), test glue
`test/PacificTogetherTest/Scripts/tunnel.lua`, runner option `-Tunnel`. UE4SS 3.0.1-1181-g83330635, lane A test pair
`C:\PTLanes\laneA`, port 7811 (link port 8811), all runs `-Headless`.

## How it works

- The game exe imports `WS2_32.dll` by ordinal (`dumpbin /imports`: 17 = `recvfrom`, 20 = `sendto`, also `WSAIoctl`,
  `getaddrinfo`, ...). The DLL swaps the exe's import-table slots that hold `ws2_32!sendto` / `recvfrom` (found by
  pointer value, one slot each: `PT|native tunnel hooks sendto=1 recvfrom=1`). Other modules (Steam, UE4SS, our own link
  socket) keep the real functions. No MinHook/PolyHook needed (UE4SS links PolyHook_2, unused here). Installed only when
  Lua turns the tunnel on; until then the game's sockets are untouched.
- `sendto` to `10.77.0.0/16`: looked up in the fake-address map; the payload goes to the link with a 4-byte header
  (UE source port, destination port). Unknown fake address: counted, dropped, reported as sent (like UDP).
- `recvfrom` on any socket: first pumps the link (non-blocking) into an inbox, then returns the oldest frame whose
  destination port equals the socket's bound port, with the sender's fake address (`10.77.0.1` for the peer Lua mapped,
  `10.77.1.N` for peers that reach us first). Otherwise the real `recvfrom`. Inbox frames expire after 2 s (frames for a
  socket that is gone, e.g. the client's first, timed-out pending connection).
- Everything runs inside the engine's own socket calls on the game thread; no extra thread; one mutex for safety.
- Probes: every 1 s per peer the tunnel sends its own ping frame (ports 0/0) and answers pongs: round-trip time
  (`rtt`, `rttAvg`, `rttMin`, `rttMax`) and a keep-alive for the Steam link, which has no close notification.
- Emulation: `PTNative_TunnelEmulate(lagMs, lossPct)` delays / drops each side's outgoing frames (probes included).
- Lua: `PTNative_TunnelUdp(port)` (link socket on `127.0.0.1:port`, 0 = any), `PTNative_TunnelSteam(channel)`,
  `PTNative_TunnelPeer("10.77.0.1", "127.0.0.1:8811" | "steam:<id64>")`, `PTNative_TunnelEmulate(lag, loss)`,
  `PTNative_TunnelStats()` -> `link= out= in= dropped= unmapped= expired= linkErrors= probes= pongs= rtt= rttAvg= rttMax= rttMin= peers= ...`.
- Test glue: `run-test.ps1 -Tunnel "udp [lag=ms] [loss=pct] [hold=s]"` sets `PT_TUNNEL`; the test mod then turns the
  tunnel on first (`tunnel_up`), points `HOST` at `10.77.0.1:<port>`, and appends `tunnel_lag_seen` (lag runs:
  >= 10 pongs and `rttMin >= 0.8 x 2 x lag`), `tunnel_session_held` (hold runs) and `tunnel_carried` (> 20 UE packets each
  way through the tunnel, >= 1 peer). Results folders are named `<stamp>-laneA-tunnel-<scenario>[-<mutation>]`.

## Derived

- The import-table hook is enough to move all of UE's game traffic onto our link with no change to the engine:
  handshake (stateless connect), join, travel with keep-listen and rejoin, and a long pending connect all work through
  it. UE accepts the fake `10.77.x.y` addresses.
- Shipping UE 4.27 has NetEmulation compiled out, so the plan's `PktLag=150 PktLoss=2` runs (Q2) must use the tunnel's
  emulation; it gives ~312 ms minimum RTT for 150 ms each way and ~2 % loss per direction, and the session survives it.
- The link is a single swap point: the Steam link (`PTNative_TunnelSteam`) uses the same frames and probes (X6).
- Mean RTT is a poor check because game-thread stalls add seconds to some samples; minimum RTT is robust.

## Guesses

- The 2 s inbox expiry and the 4096-frame cap are big enough for map loads (nothing in the inbox at the end of any run),
  but a client stalled for longer than 2 s drops the host's packets in the tunnel; UE resends reliable data anyway.
- Probes counted as answered within a tick, so the RTT includes up to one frame on each side.

## Unknowns

- Steam link under real internet RTT: only loopback-to-self was measured (X6); the two-PC test is in `docs/spikes/X6.md`.
- Whether any other engine path sends game traffic outside `sendto` (e.g. `WSASendTo`): not imported by the exe,
  so no; but the exe also imports `WSAIoctl` (not hooked; UE uses it for socket setup only, guess).
- CPU cost per packet (one `getsockname` per `recvfrom` while frames wait): not measured.
- Body / guestsave scenarios through the tunnel: not run.

Verdict: X5 passes. The session suite we ran (listen, travel, zonejoin) passes through the tunnel, and listen and travel
also under 150 ms lag plus 2 % loss per direction; each tunnel check has a mutation that fails it. Keep the a2 transport plan.
