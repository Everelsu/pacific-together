# Spike X2: world and loot (stable ids, runtime replication, loot call path)

2026-10-19/20, lane B. Scenarios `x2garage` / `x2zone` (`test/PacificTogetherTest/Scripts/scenarios/x2.lua`), headless,
port 7821, test pair `C:\PTLanes\laneB`, `main.dll` copied from the main checkout. The host opens the map with
`?listen`, spawns and possesses a `PDP_MainCharacter_C` for the guest 150 uu from its own (the `body` method), and
teleports both players next to each target, so relevancy hides nothing. Results are in
`local/test-results/<folder>`; folder names below are run ids. The zone was opened directly
(`open /Game/Maps/Wilderness/Forest/Wilderness_Forest_01?listen`), not reached through a run.

How the checks work: both sides list every actor of the world (class, path, spot, `RF_WasLoaded`, role, PendingKill).
The client writes its list to `%TEMP%\pt-x2-<port>-<tag>-client.txt` and the host diffs both (`PT|iddiff` lines). The
host announces each target in `...-targets.txt`; the client then looks for a new SimulatedProxy actor of that class
and waits for it to go. Hooks (`PT|call`, `PT|calls`) log the game's interaction and inventory functions on both sides.
Since the 2026-10-20 review: the diff skips pending-kill actors on both sides; `client_<tag>_gone` needs the actor to
have been seen, and fails as soon as the host announces its next target (after that, removal can be relevancy, see
Q2); the pickup check needs the world actor gone and one more item carried.

Verdicts:
- **Q1 stable ids: partly free.** Level-placed actors have the same full path on both sides. Spawned actors do
  not: garage stations match by class + spot only, and zone loot is a separate random pick on each side.
- **Q2 runtime replication: works for showing and removing the host's actors, not as a state sync.**
  `SetReplicates(true)` makes a host actor appear on the guest within 4 s, and the host's destroy (ours or the
  game's pickup) removes it there within 0.15-1 s. It also leaves the guest when the players walk away from it
  (relevancy), so "gone on the guest" does not mean "taken". A level-placed actor binds to the guest's own copy; a spawned
  one arrives as a second actor next to the guest's own. Guest copies run their own BeginPlay and roll their own
  contents. Attached actors land at 0,0,0.
- **Q3 call path: found for container opening only.** For taking and world-item pickup we found calls the host can
  make to do them (`ItemSlot:TransferStackIntoContainer`, `Pickup Actor`), not the path the game takes for a player:
  no UI transfer ran, and the player's own pickup press completed in only 2 of 43 runs (to hands, through
  `LongInventoryInteract`), cause unknown. Wreck scrap and anchors are known from the dumps only; the bot did not
  drive them.

Final runs (current `x2.lua`): `20261020-134215-laneB-x2garage` 32/32, `20261020-133801-laneB-x2zone` 33/33 (the
zone run started just before a log-only line, `PT|iddiff dead loaded`, was added). Earlier passes with the review
changes: `20261020-130122-laneB-x2garage` 32/32, `20261020-125651-laneB-x2zone` 33/33.

## Correction (2026-10-20): IsValid is not "alive"

Runs up to `20261020-110229` judged "gone" by `IsValid() and not IsActorBeingDestroyed()`. From Lua,
`IsActorBeingDestroyed()` read false in every run, and `IsValid()` stays true until garbage collection: the host's own
destroyed actor turned invalid 17.5 s and 33 s after `K2_DestroyActor` (`110229`, polled every 250 ms). The test now
uses the `PendingKill` internal flag (`HasAnyInternalFlags(0x20000000)`), which is set right after the call
(`pendingKill=true` in every destroy line since `111151`). Everything on day 1 about removal was measuring GC and is
replaced below: the 8-40 s delays, "a destroy of a bound level actor never reaches the guest", "`Pickup` did not
complete", and the guess that hooking `K2_DestroyActor` stopped Lua calls to it. `FindAllOf` also returns dead
actors: the guest's list in `114921` had 50 of 680 actors pending kill, the host's 0 of 1507.

## Derived

- **Stable ids:** the full path is a free stable id only for loaded actors (`RF_WasLoaded`). Garage stations and
  storage match by class + spot. Zone loot has no reliable counterpart on the guest: the guest keeps its own
  random variant per prefab group, sometimes the same one, and even a same-named one is a separate actor with its
  own contents. The host's actor is the only real one.
- Runtime replication can show host-only actors on the guest and removes them promptly, including the game's own
  pickup destroy. Pairing comes free (the replicated actor is the host's), but the replicated copy is a Blueprint
  running its own BeginPlay on the guest: own loot roll, own interactable state, own self-destroy attempts. It also
  lands at 0,0,0 when its host parent is not replicated. Replicate the look, position and existence; never trust its
  game state.
- Loaded actors bind on the guest (static NetGUID by path), and a host destroy of a bound loaded actor reaches the
  guest. So removal can go through replication for any actor the host replicates. But the guest also loses a
  replicated actor when it stops being relevant, so the guest cannot read "removed" as "taken"; that has to be a
  message.
- The interaction chain to intercept on the guest is `PDP_MainCharacter_C:Command Interact` /
  `Interact_WorldInteraction` / `Interaction_InventoryAction` (input level), or `BP_HighlightManager_C:HighlightPress`
  with `CurrentHighlight` (which object). Those give "guest wants to open / pick up object Y". On the host the same
  object can be driven through `HighlightComponent:InteractPressed`/`InteractReleased` (lootables, the game's own
  chain) or `Pickup Actor` (world items; `To Hands=true` for the balls), and the outcome is visible in
  `BP_Lootable_Base_C:*`, `ItemContainer:AddItem`/`RemoveItem` and `ItemSlot:*`. Taking out of an open container
  has no observed player path (see Unknowns).
- Any Lua "is it still there" test must check PendingKill, not only `IsValid`; `FindAllOf` results must be filtered
  the same way (the shipping mod too).

## Guesses

- The 0,0,0 position is the attachment: `AttachmentReplication` names a parent the guest cannot resolve
  (`ManageChildrenActor_*` is not replicated), so the actor keeps the origin. Detaching fixed it in all but one run.
- The prefab variant pick uses an unseeded or per-process random stream. A seed sync would not be enough anyway: the
  host's run spawn pass (crates, wrecks, barrels) never runs on the guest.
- With a real save the backpack has slots, and the player-path pickup (`Interaction_InventoryAction`) completes
  more often than 2 in 43. Both successes went to hands through `LongInventoryInteract`; a short press probably
  goes to the backpack.
- The balls refuse the backpack because of their item type (hand-only), not because the backpack was full: an emptied
  backpack refused them too (`124636`).
- The loot UI's transfer (`ContainerCursor:TransferSlot` and friends) ends in an `ItemSlot:Transfer*` call like the
  bot's. Not observed.

## Recommendation for M4 (W1, W2)

1. **Ids.** Our id for an object is: the path for loaded actors; on the host, class + spot quantised to 10 uu (taken
   at BeginPlay, before physics moves it) + an ordinal for ties, for spawned ones. The host keeps an `id -> actor`
   table and sends the id with every state message. Do not use spawned actor names. For actors the host replicates,
   the replicated actor itself is the guest's handle; the id is only needed in messages.
2. **Suppress on the guest** (destroy, or hide + no collision + `Set World Item Interactable(false)` where destroy is
   refused), right after BeginPlay: its own lootables (the variant it kept per prefab group), `BP_SpawnPoint_C` /
   `BP_ItemSpawner_C` / `BP_LeafSpawner_C` products, world items and resources it spawns in zones, its local car and
   car parts (M3), and garage storage UI contents (shown from host state). Only actors with Role 3 (local); replicated
   ones (Role 1) stay.
3. **Show host-only spawned actors by replication.** On the host, for every actor of the loot classes (lootables,
   world items, wreck templates and parts, lockboxes, gas barrels, anchors), set replicate + replicate movement after
   BeginPlay, detaching from non-replicated parents first. On the guest, ignore the replicated copy's own state: on
   arrival, clear its container and turn off its own roll / self-destroy (hook its BeginPlay paths). Removal follows
   the host's destroy (measured 0.1-1 s), but relevancy also removes it, so "taken" is always a message. Fallback if replicated Blueprints keep misbehaving: a spawn manifest message
   (class, transform, id) with guest-side spawning.
4. **Everything else goes through intents.** The guest's interaction is caught at `Command Interact` /
   `HighlightPress` with the target id. That covers opening and world pickups, not taking items in the loot UI:
   its call path is unknown (see Unknowns), and M4 must find it first (hook `ContainerCursor:*` and `ItemSlot:*`
   while a person drags items). The host runs `InteractPressed`/`InteractReleased` on its own object
   (lootables), `Pickup Actor` (world items), or `ItemSlot:TransferStackIntoContainer` for transfers, and broadcasts
   the result: opened, contents (archetype list), empty, taken. The guest's loot UI shows the host's contents. The
   guest's backpack lives on the host (P3/P5); picked-up items go there.
5. **Level-placed actors** (rare for loot) keep their path id. If the host replicates them they bind to the guest's
   copy and a destroy reaches it; other state changes (opened) are messages.
6. Keep `x2zone` / `x2garage` as the W1/W2 regression tests once suppression exists. Add checks that the guest has
   no own live lootables and the host's replicated ones sit at the host's spots with the host's contents.
