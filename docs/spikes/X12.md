# X12: the guest's backpack as data on the host, persisted next to the host's save

Question: can the guest's backpack (item ids, counts, durability, quick slots) be read and written as a small record
on the host for the guest's character, and restored after the guest leaves and rejoins, and after the host saves and
reloads, without changing the game's save format (D7, P5)?

Scenario: `test/PacificTogetherTest/Scripts/scenarios/backpack.lua` (helpers in `guestchar.lua`; API probe
`invprobe.lua`). Flow: the guest fills its backpack (4 stacks, 10 items, 2 with a set durability, 2 quick slots),
encodes it and sends it to the host; the host rebuilds it in containers of its own, saves (slot 7) and writes the
record next to the slot; the guest disconnects, wipes its backpack, rejoins; the host sends the record back and the
guest rebuilds it; the host forgets the record, destroys the guest character and reloads its save; the guest
rejoins and the host sends the record read from the file alone.

## Observations

Runs: `20261019-205030-laneC-backpack` (41/41), baseline reruns `20261020-113322-laneC-backpack` (41/41) and
`20261020-114451-laneC-backpack` (41/41), one crashed baseline `20261020-112355-laneC-backpack`, mutations
`20261020-111015-laneC-backpack-nosend`,
`20261020-111433-laneC-backpack-nopersist`, `20261020-111856-laneC-backpack-nodur`,
`20261020-112155-laneC-backpack-keepguest`; earlier crash `20261019-202424-laneC-backpack`; API probe
`20261019-190928-laneC-invprobe`.

Inventory classes (dumps: `CXXHeaderDump/PenDriverInventory.hpp`, `BP_InventoryManager.hpp`):

- The backpack is `BP_InventoryManager_C.Inventory_Player` (an `ItemContainer` with layout
  `/Game/Gameplay/Inventory/Containers/CL_Player_Backpack`, slots are `ItemTileSlot` with `Location` X,Y and
  `bRotated`), the held item `Inventory_PlayerHand`. The manager is a subobject of `DrivingGameInstance`: one
  backpack per game process.
- Quick slots: `BP_MainCharacterManager_C.HotbarShortcuts` (`UHotbarContainer`), `GetShortcuts()` returns
  `BP_HotbarShortcut_C`s with `GetShortcutItem` / `SetShortcutItem(ItemInstance)`; binding goes through
  `BP_MainCharacterManager_C:BindHotbarSlotIndex(item, index, ...)`. Index 0 and 1 bound the 2nd and 3rd entry of
  `GetShortcuts()` (record `hot:2=...;3=...`).
- Items: `UItemInstance` with `Archetype` (`ItemArchetype` asset, e.g.
  `/Game/Gameplay/Inventory/Items/Tools/Scrapper/IA_Tool_Target_ItemHarvest_Scrapper...`; `StackSize`, tile size,
  `Properties` = list of `IP_*` property structs). `InventoryBlueprintLibrary:CreateItemInstance(world, archetype, 0)`
  makes one; `ItemContainer:AddItem(item, false)` places it; `RemoveAllItems()` clears a container.
- Durability: read with `BFL_ItemPropertyUtilityFns_C:GetDurability` (`{Durability}`, `{MaxDurability}`); write with
  `InventoryBlueprintLibrary:SetItemProperty(IP_Durability, item, FName("Durability"), value)`. The full struct
  member name `Durability_5_448CDA0B4D9935979EBC4AA6A500ADAF` returns false and changes nothing; plain `Durability`
  returns true and works (both sides, every run).

Round trips (runs `20261019-205030` and `20261020-113322`):

- The record is one text line, 557 bytes for 10 items: per stack archetype path, count, X, Y, rotated, durability
  per item; then the hand; then quick slots as `index=container@X,Y`.
- Guest to host and back went over `PlayerController:ServerExecRPC` / `ClientMessage` hooks (a test stand-in for the
  M4 intent channel); the host parses it field by field.
- The host rebuilt the record in two containers of its own, made with
  `CreateContainerWithLayout(inventoryManager, text, Inventory_Player.Layout)` and filled with `Layout:EmplaceSlot`
  at the recorded X,Y and rotation: re-read, the encoding equals the received one (`host_container_roundtrip`), and
  the host's own backpack is unchanged (`host_inventory_untouched`). Plain `AddItem` on such a container returned false
  with 0 slots in the probe; `EmplaceSlot` is what places items there.
- Those host-side containers are not kept alive: gone 82 s after creation (`IsValid()` false; 185 s in run
  `20261019-202424`; 71 s in `20261020-113322`, looked up by name). Run `20261020-112355` created them one step
  (8 s) before filling them and the host crashed in that step with `EXCEPTION_ACCESS_VIOLATION 0x00000159b249db20`
  (the PenDriverPro log has no line about it). Since then the containers are created, filled and read in one step.
- A post-hook on `BaseSaveGameManager:SaveGame` (slot taken in the pre-hook; the post callback gets the return value
  in the first parameter) wrote `Saved/SaveGames/odsave7.pt-<SteamID>.txt` beside `odsave7.sav`; the game's own
  `.sav` is written by the game alone (`host_file_written`). Beside it the game keeps timestamped copies of the slot
  (`odsave7-backup-2026.10.19-20.48.11.sav`, ...); our side file has no such copies.
- Leave and rejoin: after `disconnect`, a wipe of the guest's backpack and quick slots, rejoin and a fresh spawn, the
  guest rebuilt the record into its own backpack and quick slots and re-read an identical encoding, durability
  included (`guest_restored_after_rejoin`).
- Host save and reload: the host cleared its memory of the record, destroyed the guest character and called
  `LoadGame(7)`; it came back listening in `RB_Garage` (native keep-listen), read the record from the file alone
  (`host_file_loaded`), its own backpack count was unchanged, the guest dropped to the main menu, rejoined, and
  rebuilt an identical backpack (`guest_restored_after_reload`).
- Crash: run `20261019-202424` called `LoadGame` with the guest character still in the world; the host died with
  `EXCEPTION_ACCESS_VIOLATION reading 0x20` right after `BeginTearingDown for RB_Garage` (the PDCoopNet exp13 crash).
  Mutation `keepguest` (skip `destroyGuests` before `LoadGame`) reproduces it: same exception, same last log lines
  (`LoadMap: RB_Garage?listen`, `BeginTearingDown`, NetDriver shutdown), 29/34. The 41/41 runs destroy the guest
  character first and reload cleanly.
- Mutations, each failing exactly the checks it targets:
  `nosend` (host never sends the record back): `guest_restored_after_rejoin` and `_after_reload` FAIL, 39/41.
  `nopersist` (no side file, record forgotten before the reload): `host_file_written`, `host_file_loaded`,
  `guest_restored_after_reload` FAIL, 38/41; the rejoin restore before the reload still passes.
  `nodur` (rebuild skips durability): `host_container_roundtrip`, both `guest_restored_*` FAIL, 38/41.

## Derived

- The guest's backpack only has to exist as real game containers on the guest (its own `Inventory_Player`); on the host
  it is data. The record is enough to restore everything we checked with the game's own functions.
- Persisting next to the slot with a SaveGame post-hook keeps the game's save format untouched and follows every host
  save that goes through `SaveGame` (autosave too, see Guesses).
- The host must remove guest characters before any map teardown it starts (LoadGame, travel); M2 must own that.
- Containers made with `CreateContainerWithLayout` are collected once no game object references them; a Lua reference
  does not keep them alive. Using one after that most likely crashes the game (see Guesses).

## Recommendation for M4 (P3, P5)

- **Runtime:** the guest's backpack lives on the guest, in its own `Inventory_Player` and hotbar (X4: pickups land
  there through the game's code). The host keeps only the latest record per guest SteamID, in memory, as data (not as
  host-side containers: they get collected).
- **Updates:** the guest sends its record (the format above, or the same fields in the intent channel's encoding) when
  its backpack changes (debounced, e.g. 2 s after the last change) and on leave; the host stores it as-is after
  validation (known archetype paths, counts within `StackSize`, at most the backpack's slots).
- **Persistence:** on every host `SaveGame` of slot N, write `odsaveN.pt-<SteamID>.txt` per known guest beside
  `odsaveN.sav`; on host load of slot N, read them; on join after the handshake (S4 gives the SteamID), send the guest
  its record and the guest rebuilds (wipe, `CreateItemInstance`, `SetItemProperty(..., "Durability", ...)`,
  `EmplaceSlot`/`AddItem`, `SetShortcutItem`). No file = a new guest starts empty (D7). Write the file atomically
  (temp file + rename) so a crash mid-save cannot lose it, and keep the previous one as `.bak` the way the game keeps
  slot backups.
- **Trust boundary:** the record comes from the guest; parse it field by field (as the scenario does), never `load()`
  it.
- Before the host starts any map teardown with a guest character in the world, destroy the guest character first.

## Guesses

- The `20261020-112355` crash is the GC freeing the host-side containers between the step that made them and the step
  that filled them (they are collected within 71-185 s in other runs, UE's default GC interval is about 60 s); one
  crash, not reproduced on purpose.
- Items whose state is not durability (fuel in a fuel can, battery charge, chart data, decal colour) carry other
  `IP_*` properties that this record drops (the fuel can's fuel level was not checked). `GetDataBlockDump`
  shows an item's full data block and is the likely source for a complete record.
- Autosave goes through `BaseSaveGameManager:SaveGame` like the manual save (X10 blocked it there), so the post-hook
  covers it.

## Unknowns

- Other item properties than durability (see Guesses); nested containers (items that are containers).
- A real SteamID: the scenario uses a stand-in id; the handshake (S4) must provide it.
- What the game's menu does to our side files when a slot is deleted or overwritten by a new game: not checked.
- Behaviour with a full backpack (the restore's fall-back `AddItem` placement).

## Verdicts

- Read and write the guest's backpack as a small table: **yes** (ids, counts, grid position, rotation, durability,
  hand, quick slots).
- Restored after leave and rejoin: **yes**. After host save and reload: **yes**, from the side file alone.
- Game save format unchanged: **yes**, side file next to the slot.
- Design: **guest-held backpack, host-held record per SteamID, side file per save slot.**
