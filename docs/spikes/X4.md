# X4: guest interaction through the game's own code path

Question: with the guest owning its own `PDP_MainCharacter_C` (host spawns it and possesses it with the guest's PC, as
in the `body` scenario), can the guest use the game's interaction (look at an interactable, press interact) on doors,
a container and a pickup, what happens on the host and the guest, and which single-reference managers do the guest's
actions go through?

Scenarios: `test/PacificTogetherTest/Scripts/scenarios/interact.lua` (garage: starter storage + a spawned pickup),
`interactzone.lua` (forest zone: lootable backpack + abandoned-car door, observe only), shared helpers in
`guestchar.lua`, the one-instance API probe `invprobe.lua`. Results under `local/test-results/`.

## Observations

- Spawning a second `PDP_MainCharacter_C` on the host flips `BP_MainCharacterManager_C.CharacterActor` to the new
  character (`managerFlippedOnSpawn=true` in every run). `guestchar.spawnGuest` writes the host's own character back
  after `Possess`; after that `CharacterActor=own` on the host for the whole run (the guest side: see Zone).
- `BP_MainCharacterManager_C` (holds `HotbarShortcuts`) and `BP_InventoryManager_C` (holds `Inventory_Player`,
  `Inventory_PlayerHand`, trunk, garage, ... containers) are subobjects of `DrivingGameInstance`: one each per game
  process, not per player (full names in the invprobe log).
- `BP_HighlightManager_C` on the guest traces from the guest's own camera (`highlightPOV-ownCam=0`) and highlights
  the guest's local copy of the target. Aiming with `SetControlRotation` at the target's `HighlightCollision`
  component highlights the starter storage and the pickup within 1 s (`guest_highlight_*` PASS).
- Pressing interact the way the input does (`PDP_MainCharacter_C:"Command Interact"(true)` then `(false)`) fires
  `HighlightComponent:InteractPressed` on the guest (instigator argument `none`) and the game's own effect runs on the
  guest: the storage opens the guest's inventory menu (`menu=false -> true`), the pickup lands in the guest's own
  backpack (`inv=0 -> 1`). The world item's `Instance` stays set and `bHidden=false` 3 s after the pickup on both sides.
- Nothing reaches the host: `InteractPressed` never fires on the host (`presses=0`) and the host's menu, inventory and
  its copy of the target are unchanged (`host_unaffected_*` PASS). The guest's interaction is purely client-local.
- The host running the same code for the guest's character on its own copy:
  `Highlight:InteractPressed(guestChar)` on the storage opens the **host's** inventory menu (`menu=false -> true` on
  the host); `guestChar:"Pickup Actor"(item, false)` puts the item into the **host's** backpack (`inv=0 -> 1` on the
  host). The guest sees neither. (`PT|hostrun` log lines, same in both runs; logged, not an asserted check.)
- `BP_CarManager_C.NewCarActor`: host's car with role 3 (authority) on the host; on the guest a `BP_PlayerCarNew_C`
  with role 1 (simulated proxy).
- Doors: `RB_Garage` has no `BP_Door_Single_C` / `BP_Door_Double_C` on either side. The nearest door is the car's

  Car doors are M3 (C1); the door target was dropped from the garage run.
- Mutations, each failing exactly the checks it targets: `noaim` (guest never aims): `guest_highlight_*` and
  `guest_effect_*` FAIL, 22/26, so pressing interact without a highlight does nothing; `nopress`: `guest_effect_*`

  - The host's `InteractPressed(guestChar)` on its lootable backpack changed nothing visible on the host (`menu=false`).

## Derived

- The guest's own process has a complete single-player interaction stack (character, highlight, inventory and
  character managers; in the garage all pointing at the guest's own character), so the game's code path works on the guest with no
  patching, but only against the guest's local copies of world actors and its local inventory.
- On the host every single-reference manager points at the host's player, so running an interaction on the host "as"
  the guest routes its result (menu, backpack, hotbar) to the host. Host-side execution of interactions for the guest
  is the wrong model for anything that touches inventory or UI.
- The map of managers the guest's actions go through:
  | Manager | On the guest | On the host, for the guest's character |
  |---|---|---|
  | `BP_MainCharacterManager_C.CharacterActor` | guest's own in the garage, the host's character in the zone | host's character (flips to the guest on spawn, must be restored) |
  | `BP_InventoryManager_C` (backpack, hand, menu) | guest's own | host's own: guest pickups and container menus land on the host player |
  | `BP_HighlightManager_C` | guest's camera and copy | host's camera only; never traces for the guest |
  | `BP_CarManager_C.NewCarActor` | replicated host car (role 1) | host's car |
- What breaks: anything the guest does changes only its own copy (the host's world, containers and pickups never
  change, so loot duplicates); and anything the host does for the guest lands on the host player.

## Recommendation for M4 (P2, P3)

- **Guest-local interaction, host-authoritative effects.** Let the guest's game run the interaction and its UI
  locally (highlight, menu, backpack, hotbar all work there). Hook the effect points on the guest (`Pickup Actor`,
  container transfers, scrap/anchor completion), send an intent with the target's stable id (X2) to the host over the
  intent channel, and have the host validate it against its copy and apply only the world side (destroy or hide the
  world item, change the container's contents) and broadcast the result. The item itself goes into the guest's own
  backpack on the guest (P3 needs no host-side backpack at runtime).
- Do not call interaction functions on the host with the guest's character as instigator.
- Gate the guest's local copies (X3) so the host's state is what the guest sees: a guest pickup is accepted only after
  the host confirms it, else rolled back.
- Keep `guestchar.spawnGuest`'s `CharacterActor` restore in M2's spawn code, and on the guest set `CharacterActor`
  to its own possessed character after every possess (it pointed at the host's character in the zone).
- Zone loot needs the host's world on the guest first: the guest's lootables are its own, elsewhere and under other
  names, and abandoned cars do not exist on the guest. Interaction there depends on X2/X3 (stable ids, replicate or
  suppress the guest's copies).

## Guesses

- `"Command Interact"` is the same path the keyboard binding takes (it is the character's input function); not
  checked against a real key press.
- The world item staying visible after the pickup is an asynchronous destroy or pooling; not checked longer than 3 s.

## Unknowns

- World doors (houses, gates) in zones: none in the garage; not searched in the zone survey.
- Whether a guest interaction works in a zone while its `CharacterActor` points at the host's character: no guest
  lootable could be reached to try it.
- Why `CharacterActor` differs between garage and zone on the guest (guess: whichever character's BeginPlay runs last
  on the guest wins, as on the host at spawn).
- Tools (scrapper, cutter) and anchors on the guest: not run.

## Verdicts

- Can the guest use the game's own interaction? **Yes, locally**: highlight, container menu and pickup work on the
  guest through the game's code; nothing reaches the host.
- Can the host run it for the guest? **No**: results land on the host player through single-reference managers.
- Doors: **not answered** for world doors; car doors belong to M3; abandoned-car doors exist only on the host.
- Zones: **blocked by duplicates**: the guest's lootables are other actors in other places (needs X2/X3 first).
- Design: **guest-local interaction + host-authoritative intents** for P2/P3.
